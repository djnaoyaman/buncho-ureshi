# バランス調整の個別公開計画

基点: `10862b21b8f499db51814d16c7c7f456fd43a4bd`。
依頼: 統合案を一つずつ対応・検査・公開する。未確定だった通貨・死亡・移行の仕様は実装前に確定する。
1件目は`b971bc8`で公開済み。公開前CI成功・配信8ファイル一致を確認。利用者が提示条件を承認済み。以下の受取・移行仕様で実装・検査を進める。公開完了はCIと配信照合後に記録する。

各公開は関連検査→main競合確認→公開前CI→Pages成功→配信ファイル照合まで行ってから次へ進む。
既存検査を削除して通さない。保存破損やルールの不明確さが残る状態では公開しない。
実機の手動確認は利用者が担当する。次期機能・全体整理・素材更新を同じ差分に混ぜない。

## 1件目の承認済み仕様

- 日本時間の日付で1日1回、訪問して確認した日だけ30 Gold。未訪問日分を後から加算しない。
- 受取ボタンで暮らしを確認する。対象は家の家族で、来客のお世話を受取条件にしない。
- お世話できる家族のごはん・元気が満タンで、清潔度20以下なら掃除後に受取可能とする。
  卵・ひなは観察対象とし、給餌・ふれあいを強制しない。
- 病気・けがの通院完了は受取条件から除外する。Gold不足で通院も受取もできなくなる循環を避け、
  受取とは別に必要な通院を案内する。飼育員が通常のお世話を済ませていれば受取可能。
- 操作ごとの4 Goldは廃止。既存のGems報酬・残高・所持品・飼育員価格24 Gold/日は変更しない。
- 旧形式には当日のGold受取合計がないため、移行日は追加支給せず、日本時間の翌日から新方式を開始する。
  新規の世界は初日から対象。既存残高を差し引いたり、推測で受取額を補正したりしない。

## 保存と実装範囲

現行 `economy.version=1` は固定項目の厳格検証で、受取済みの日付を持たない。
受取済み記録はGoldの加算と同じ保存トランザクションで扱い、二重クリック・再読込・複数タブで重複支給しない。
独立したlocalStorageキーだけで支給済みを記録すると、Gold保存との片方失敗を防げないため採用しない。

既存の厳格な版管理に沿って必要な保存項目と移行を追加し、旧形式の原本を保管する。
旧v11移行原本・リセット用バックアップを上書きしない。旧画面からの書込は新形式の検証で拒否する。
名前・個体ID・家系・つがい・日記・墓・持ち物・Gold/Gems・乱数列の既存値は保持する。
手動の全保存読込では、現在と同様に世界全体とその受取状態を一緒に扱う。端末全体の不正対策は主張しない。

## 1件目の検査計画

- 新規/旧形式、1/2/6羽、卵・ひな・成鳥、来客の有無、飼育員中、病気/けが、全員が墓にいる状態。
- 条件を満たす前後、Gold不足での治療案内、日本時間の日付変更、停止中、時計の巻戻り、未訪問日。
- 旧方式を使った当日の移行、翌日受取、連打、同時2タブ、再読込、支給済み保存の読込、保存失敗。
- Gold残高上限では未支給なのに受取済みにしない。失敗時は元の残高と受取記録を保持。
- 旧版の原本/移行原本/リセット用保存を保持。無関係な名前・血縁・墓・Gems・乱数列の一致。
- 実ブラウザで条件表示→受取→残高更新→再読込→再受取不可を確認。既存の保存/設定導線を維持。
- 関連検査と既存の全Node/公開前ブラウザCIを維持し、数値を下げたりskipして通さない。

保存形式を追加した後は、旧コードへの単純なrevertでは新しい保存を読めなくなる。
支給を停止する場合も新形式の読込を保つ修正として戻し、元の保存を初期化しない。

  初期Gold0からは最初の受取後に1日契約が可能。欠席日の収入はないので長期契約には前払い資金が必要。

## 2件目：清潔度36時間

利用者が36時間案を選択。基点は公開済み`b971bc8cf77e6fa6970495fc2383887fcf122266`。
- 1分につき1から、27分につき1の整数減少へ変更。掃除後100→20は2,160分＝36時間。
- 同じ掃除時刻から、24時間後47、36時間後20、45時間後0。20以下の掃除案内・Gold受取条件は維持。
- 現在値とlastCleanTickを保持。保存版13、保存項目もそのまま。再読込で端数の時間を失わない。
- 初期tickまたは最後の掃除tickを起点に差分を計算し、短い再開と一括不在で減少量を揃える。
  既存の100状態では引き継いだ周期位置により最初の1減少が27分以内となる。値の初期化・補填はしない。
- 一時停止で汚れが進まない従来の扱いを維持。給餌・通院の実時間期限、寿命、Gold・Gemsは変更しない。
- ヘルプに36時間と一時停止の扱いを追加。ゲームの時間目安として示す。
- 境界、短い再開、一括不在、再読込、掃除の周期リセット、現行セーブ保持、Gold条件、死亡期限を検査する。
- 戻す場合は同じ保存形式のまま減少周期を修正する。値・掃除履歴や保存の初期化は不要。

追加の不在検査で、飼育員1日契約後36時間留守にすると清潔度20、24時間時点で開いた場合73となる差を再現。
契約中の掃除を途中復帰時だけでなく、契約終了の計算境界でも反映し、どちらも73へ揃える。
料金24 Gold・契約期限・通院期限・最後の手動掃除tickは変えない。短い再開・時計巻戻りでも検査する。
既存ヘルプは全文一致の検査を維持し、36時間の説明1段落だけを追加として個別に検査する。

復帰直後のお世話が物語の時間更新より先に実行される経路でも20/73の差を再現したため、
床の計算区間に含まれる既知の契約終了時刻から、支払い済みの掃除を反映する。
健康の時計を巻き戻さず、病気を過去に推測しない。分の途中で終わる契約も同じ結果となることを検査する。

最終ローカル検査：全Node1,608件成功、Chromium/WebKitの関連ブラウザ72件成功。
構文387ファイル・既存コンテンツ検査成功。skip追加・検査削除はしていない。
汚れによる新しい体調リスクに至る時刻は遅くなるが、既にある病気・けが・お墓の日時を変更しない。
乱数の追加呼出はなく、成長・繁殖の式とGold/Gemsの付与額は維持する。

## 次の仕様判断候補：不在中の小さな出来事（まだ未承認・未実装）

現行のofflineSummaryは経過tick等の5項目のみで、日別の出来事や支給済み相当の重複防止記録を持たない。1日最大1件を複数タブ・再読込でも守るため、同じ保存トランザクションに日付と報告を追加する案。
- 30分以上の不在を対象とし、日本時間で1日最大1件。帰宅時の報告は直近7日分まで。
- 既にいる家族・既知の友達の小さな報告に限る。新しい個体を自動生成せず、この報告によるGold/Gems・友好度の加算はしない。
- 入居・つがい・事故を追加で自動決定しない。既存の成長・お世話・通院・寿命の処理は維持する。
- 物語停止中は生成しない。更新前の不在をさかのぼって生成しない。
- 保存形式の追加と移行が必要。既存の全値を保ち、更新前14の原本は過去の13/12/11原本と別保管する。既存の日記や記録日時を変更しない。
- 候補の段階であり、日数・内容・保存影響の確認が取れるまで実装しない。
