# エンディング拡張 第1回：セーブ保護の準備

今回の公開は保存形式 v19 のまま。新エンディング、v20への移行、新しい保存項目、育成・通貨・報酬・RNG・名前・家系の変更はない。

## 既存機構と不足

既存の厳密な版別検査、原子的なIndexedDB transaction、Web Locks付きlocalStorage fallback、旧版の移行前コピー、リセット前コピー、import時の確認・世代ID交換・失敗時保持を再利用する。保存バックエンド失敗時に別の庭へ切り替えない方針は維持する。

従来の書き出しは `transact(advanceTo)` に依存していた。容量不足で書き込みが失敗すると、読み取れる保存も書き出せず、書き出すだけで時間や健康更新が進む可能性があった。新しい `exportSnapshot` は保存済み原本をread-onlyで取得し、対応版の検査を通してから元の版と値を出力する。IndexedDBはtransaction完了後のみ返す。localStorageは同じWeb Lockで読み、裸JSONの元の文字列も保持する。リセットwrapperはcurrentのみ書き出し、wrapperとbackupは変更しない。memory modeはそのタブのコピーであることを明示する。

失敗した変更を保存済みと偽らない。壊れた値・未来版・保存なし・読取り拒否は書き出しを拒否し、元データに触れない。書き出し結果は保管箱の既存DOM内で更新し、全画面をrenderしない。既存の保存エラー表示は消さない。

## 将来の移行前原本

既存のバックアップ鍵を保ったまま、対象版の分岐をSAVE_VERSIONと元版から導出する。v19稼働中はv19の自動コピーや移行はしない。次回に版を上げる場合、対応する移行検証が成功した原本は既存transaction内で `migration-backup-v19` に初回だけ保全できる。バックアップ取得も版番号を検査し、v19指定をv11へ誤って読み替えない。localStorageは原本をコピーできなければ本体の更新へ進まない。IndexedDBはコピーと更新を同じtransactionで行う。

第2回は別途承認・設計が必要。実際の移行関数、v19原本fixture、容量不足によるbackup書込み失敗・transaction abort、複数タブ、既存コピーの不変性、旧クライアント拒否、復旧検査をその公開で実施する。この準備だけで将来の移行を安全と認定しない。

## 利用者の保全・復旧

1. 設定 → 保存とリセット → 保存ファイルを書き出す。最後に端末保存できた庭を取得する。ダウンロードしたファイルはブラウザ外にも保管する。
2. 保存失敗時はリセットやブラウザデータ削除をしない。まず書き出し、他タブを閉じて空き容量・保存設定を確認する。書き出しにも失敗する場合は元データを残して原因を調べる。
3. 復旧時は保管したJSONを読み込み、既存の確認を経て庭を交換する。ファイルの時点へ戻り、その後の通貨・報酬・記録とは合流しない。今回の機能が自動的に巻き戻すことはない。
4. 一時メモリの庭は端末に保存された原本ではない。タブを閉じる前にファイルを保管する。

## 検査と公開

原本の完全一致・読取り専用・失敗した編集を含まないこと・原本の版・閉じた接続・別タブの確定順・旧版/未来版/破損・reset wrapperをNodeで検査。Chrome/WebKitは320/375/402pxの容量不足後export、読取り失敗/再試行、native export/import/reset/レイアウト、前回の演出タイマー/横向き復帰を対象とする。実機iPhone 7/iOS 15.8.8とiPhone 17 Proは利用者が確認し、WebKit自動検査と区別する。
