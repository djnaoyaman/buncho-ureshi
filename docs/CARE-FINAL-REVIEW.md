# お世話ルールの実装前確認と確定部分の修正

作成日 2026年11月12日。照合元 main `e69a87c91f99b01693fd8c7028b85568b8a7ab49`。着手時の未コミット変更なし、未マージPRなし。

## 今回公開する範囲

- ゲージがいっぱいでも、なでると短いしぐさと返事を返す。無報酬の反応では鳥の状態、成長、食事期限、日記、通貨、乱数を変えない。音は従来どおり回復があった場合だけで、消音と動きを減らす設定を維持する。
- 個体画面の「次のお世話 ○時」を外す。現在の定時のゲージ更新そのものは未変更で、説明欄には現在の時刻ルールを残す。連続減少へ変更したと説明しない。
- 全員の食事と元気が満タン、床が20より上で落とし物がなく、未治療の家族や敵の接近がない場合に、直前の保存が成功してからだけ区切りの案内を出す。卵・ひなに手動給餌は要求しない。保存できない場合や一時記憶だけの動作では「ほぞんした」と表示しない。再起動で過去の成功表示は復活させない。
- 短い日本語で、反応・実際の食事・お礼の違いを説明する。説明欄の漢字はふりがな付き。既存のとじる操作で終了できる。
- 本番から参照しない計算モデルと96条件・例外12条件の試算を追加する。採用前の値を保存形式へ混ぜない。

## 未確定の重要判断は3点

添付指示書は20/30/40の減少率、下限40、H基礎額・追加上限、健康保護を採用済みとしないよう指定している。以下は提案であり、本番未採用。

1. 減少は実時間で30/24時間、下限40を第一候補とする。現在40未満の値は持ち上げない。端数を持ち越し、加入・成長と契約区間を分ける。20/40との比較は別表。
2. H案で家庭30 Gems/訪問日を基礎とし、追加は家庭10 Gems/日までを試算。追加0なら手動回復と飼育員の収入差はなくなる。追加を付けるなら、落とし物8 Gemsと回復報酬を共通の追加枠として設計する必要がある。受取は特定の時刻や満タンを条件にしない。既存30 Gold・ガチャ価格20/50/100・確率・所持品は維持する。
3. 不在だけを理由とする不可逆な喪失を避ける保護を推奨するが、現状の健康を勝手に変更しない。選択肢は現行維持／不在中は非致死的なお留守番状態／復帰から24時間の猶予。猶予方式でも長く戻れない家庭には再度期限が生じる。非致死的方式は既存病気・けがも不在中の期限切れだけで死亡させず、復帰時に通院を案内する。いずれも寿命・事故は別、既に亡くなった個体を戻さず、契約前に確定した結果を取り消さない。具体的な境界処理を同じ変更内で検査する。

[全条件の比較試算](CARE-MODEL-COMPARISON.md)。基礎30/追加10は比較用入力であり、承認された報酬ではない。

## 現行との照合結果

- `care-schedule.js` は7/17/20時、土日祝は12時も。枠を越えた観測でfood/energyを最大40減少、下限40。複数枠を不在で越えても1回。前回のコード前提と一致。
- `applyScheduledCare` は実回復が1〜20でも食事6/交流5 Gems。従って連続減少への置換だけでは微小給餌の連打が有利になる。`fullMeal` と `produceDroppings` は別経路で8 Gemsを生む。満腹の再給餌は無効で、健康期限も発生待ちも更新しないことを追加検査する。
- `petBird` は満タン時に永続状態を変更しない。今回の短い反応は表示だけで返す。`talkToBird` は既存の気分・play・記憶・しぐさを保つ。元気満タンではGemsは増えず、会話だけで給餌時刻も延びない。既存遊びの状態変化を「すべて反応のみ」とは扱わない。
- `life-care.js` は住人の給餌から72時間、food/energy両方40以下の観測継続24時間、床20以下の観測継続24時間、発症後24時間の治療期限。新たな未観測の過去の病気を推定せず、観測時から治療猶予を与える。けが・10年寿命・事故は別経路。
- 飼育員は実時間1日24 Gold、契約中の食事・元気・床と治療を保護。契約満了後は再び実時間の期限が進む。全員が満タンでもふれあいはできる。
- `economy.js` の家庭30 Goldは満タン・必要な掃除が条件。医療は受取条件に入っていない。今回の「お世話の区切り」は医療を隠さない条件を別に持つ。Goldの受取可と健康上の完了を混同しない。

## 次の実装の依存関係と保存計画

- `care-schedule.js` の `careDay/careWindow` は `economy.js` の庭の枠・自動贈り物の平日30/休日40上限と保存検証にも使う。定時のお世話から分離してもAPIと祝日データを削除しない。
- `engine.js` の `advanceTo`、`feedBird/petBird/talkToBird`、`family-care.js` の一括処理を同じ実回復記録へ接続する。個別と一括で別の報酬計算を持たない。
- 現行 `careSchedule` は `seenAt/windowAt` の2フィールドに厳密検証される。新時計・端数・家庭報酬履歴を入れるなら、版上げ、`validateVersion/readCompatibleWorld/parseSave/serializeWorld`、`game-store.js` の検査・バックアップ・輸出入・時計リベース・同世界復元を一体で改修する。今回は保存形式を変更していない。
- 移行前の保存を復旧できる形で保持し、検査・保存失敗は元の保存を書き換えない。移行時刻以前の不在に新減少を遡及しない。既存健康期限を初期化しない。初回移行と既存期限確定の順序をテストする。
- 加入や巣立ちの時計は実時間登録を新方式の起点とし、物語tickを実時間へ単純換算しない。契約の開始/終了/延長を区間として扱う。
- 同じ世界の2タブは既存のfresh-stateトランザクションとrevision照合を使う。異なる世界の報酬記録を混ぜない。復元は通貨と状態を一緒に戻し、報酬だけ足し直さない。
- OS時計の逆行は差分を0とし、異常な前進は有界な区間計算で扱う。大幅な前進の具体的上限を採用する場合も別途決定する。完全な不正防止は主張しない。

## 検査と利用者の確認手順

自動検査はCIの全Node検査と、明示したChrome/WebKitの対象検査。満腹の無報酬反応、保存失敗時の非表示、未治療時の非表示、旧時刻境界・保存・健康の回帰、表示拡大、スクロール保持を確認する。実施結果はPRと公開ワークフローを根拠に記録する。モデルは同じ経過を137分割しても一致、契約の境界、旧低値、下限、時計逆行、JSON再読込で端数保持を検査する。

実機確認は未実施。iPhoneで文鳥の食事・元気をいっぱいにし、なでた返事を確認する。次回時刻が出ないこと、最後の保存後だけ区切りが出ること、音なしでも分かることを確認する。未治療の状態では病院の案内が出ることも確認する。暮らしのメニュー・あそびかたを途中までスクロールして、数秒待っても上に戻らないか確認する。ゲーム内の健康ルールは実際の鳥の飼育方法ではない。
